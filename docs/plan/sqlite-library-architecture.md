# SQLite shader library architecture

Status: implemented foundation  
Last updated: 2026-08-22

## Purpose

Shader Pocket keeps multiple projects and their recovery history in one portable SQLite database.
The data model, SQL schema, migrations, validation, and asynchronous repository contract are
platform-neutral. The browser and a future React Native client only differ at the SQLite driver and
file-sharing boundaries.

## Platform layout

```text
Shared TypeScript
├── ShaderDocument model and migrations
├── repository contract
├── SQLite schema/version constants
├── import validation
└── snapshot hashing and retention rules

Browser adapter
├── SQLite WASM in a dedicated worker
├── OPFS-backed live database
└── browser download/upload for portable backups

Future React Native adapter
├── Expo SQLite
├── the same SQL schema and migration sequence
└── native document picker and share-sheet integration
```

Browser UI and React Native UI are deliberately outside the shared boundary. CodeMirror, DOM
layout, file inputs, and `HTMLCanvasElement` remain browser-specific. Shader document operations,
storage behavior, import rules, and recovery semantics remain reusable.

## Database identity and schema

- Filename: `shader-pocket.sqlite3`
- SQLite `application_id`: `0x53504b54` (`SPKT`)
- Initial `user_version`: `1`
- IDs: UUID strings generated by the application

Tables:

- `projects` stores document identity, title, active pass, document schema version, and timestamps.
- `passes` stores ordered pass source and metadata with cascading project deletion.
- `snapshots` stores immutable serialized documents, content hashes, reasons, and timestamps.

Small device-specific preferences, including the last active project, stay outside the portable
database. This prevents moving a library from unexpectedly carrying display or device state.

## Persistence and recovery

The browser opens SQLite in a worker and persists its live file in the origin-private file system.
If OPFS is unavailable, the repository falls back to an in-memory database and visibly reports
`Memory only`; it never claims that data is durable.

Documents save after a 450 ms edit debounce. A unique recovery snapshot is created after 30 quiet
seconds and before reset, project import, library import, and snapshot restoration. SHA-256 content
hashes deduplicate unchanged snapshots. The latest 50 unique snapshots per project are retained.

The previous localStorage document is imported once when an empty database first opens. A migration
snapshot is created before the legacy keys are cleared.

## Portable backup rules

Single projects continue to use `.shaderpocket.json`; active source continues to use `.frag`.
Whole-library backup exports a consistent SQLite image from the live connection, not a raw copy of
an independently changing OPFS file.

Library import validates both `application_id` and `user_version`. It merges projects by default.
Project or pass ID collisions cause the imported project, passes, and snapshots to receive a
consistent set of new UUIDs. Invalid recovery rows are skipped without discarding otherwise valid
projects.

Whole-library replacement is intentionally not exposed as an ordinary import action. A future
explicit disaster-recovery command must export the current library before replacing it.

## React Native continuation

A native application should implement the existing `ShaderRepository` interface with Expo SQLite
and run the same migrations before rendering project data. Native code should use a document picker
to copy an imported database into app-controlled storage and a share sheet to export a consistent
backup.

The renderer should be separated from DOM canvas ownership before native work begins. Expo GL can
provide a WebGL-shaped context, but the required GLSL ES 3.00 and WebGL2 feature set must be tested
on the supported Android and iOS device matrix. The editor UI needs a deliberate native strategy;
CodeMirror can remain in a WebView or be replaced without changing the repository or document
model.
